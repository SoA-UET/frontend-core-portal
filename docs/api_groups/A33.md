# A33 Group

This is the group of APIs between
the [Partner's Knowledge Update Service](../services/partner/S12_Partner_Knowledge_Update_Service.md)
and [Partner's Local Knowledge Service](../services/partner/S11_Partner_Local_Knowledge_Service.md).

This API consists of 1 API.

## A33

This API is based on RabbitMQ.

The API has 1 method.

### A33 Method: `update_local_knowledge`

Update types:
- `"validated_update"` - Knowledge validated by Core, ready to apply
- `"sync_update"` - Periodic synchronization from Core
- `"correction_update"` - Correction of previously stored knowledge

Response body format:

```json
{
    "id": "the corresponding request id",
    "result": {
        "status": "success or error",
        "content": "the return value of the called method"
    }
}
```

On success, the content would be:

```json
{
  "updated_count": 2,
  "inserted_count": 0,
  "deleted_count": 0,
  "skipped_count": 0,
  "update_id": "local_update_5678",
  "timestamp": "2025-12-08T11:45:15Z",
  "message": "Local knowledge updated successfully"
}
```

On failure (`status == 'error'`), the content would
reflect what is going on. If the failure is
caused by some `Exception`, the content should
be `str(e)` with `e` being the `Exception` instance
that was the culprit.

In special error cases:
- If `source` is missing or invalid, the content must be `"Invalid or missing source field"`
- If `update_type` is unsupported, the content must be `"Unsupported update type: <type>"`
- If `df` is empty or malformed, the content must be `"Invalid dataframe format"`
- If `validation_id` is missing for `validated_update` type, the content must be `"Missing validation_id for validated update"`
- If database update fails, the content must be `"Local database update failed: <details>"`
- If index refresh fails, the content must be `"Search index update failed: <details>"`

## Queue Configuration

- Request Queue: `partner_knowledge_update_requests`
- Response Queue: `partner_knowledge_update_responses`

Both queues should be configurable via `.env` file with the following variables:
- `PARTNER_KNOWLEDGE_UPDATE_REQUEST_QUEUE`
- `PARTNER_KNOWLEDGE_UPDATE_RESPONSE_QUEUE`

## Notes

- Updates are transactional - if any part fails, the entire update is rolled back
- The service automatically updates vector embeddings and search indices after successful database update
- Duplicate service codes are handled by updating existing records rather than inserting new ones
- All updates are logged in the Partner Knowledge Update DB for audit purposes
- The `update_metadata` provides traceability for compliance and auditing
